## 4. Phase 2.1：Perception → Household Memory → 动态 Object Pregrasp

### 实现

新增 `homeagent_perception` package。

仿真感知边界：

```text
/gazebo/model_states
        +
/amcl_pose
        ↓
GazeboObjectPerception
        ↓
world -> map frame alignment
        ↓
MemoryObserve(object-cup)
```

第一版后端使用 Gazebo ground truth，是为了先验证接口和数据闭环；后续替换 RGB-D / YOLO / VLM 时，下游 Memory / Context / Safety / Nav2 contract 不变。

Object Memory 新增：

- 最新 observation pose；
- observation timestamp / confidence / source；
- `mobile_pregrasp_offset`；
- `pick_pregrasp_joint_target`；
- `pick_approach_joint_target`。

Context 支持：

```text
navigate(target="object_pregrasp:cup")
```

解析过程：

```text
object Memory
→ fresh observation
→ mobile_pregrasp_offset
→ trusted resolved_target_pose
→ Safety
→ Nav2
```

缺失 observation、过期 observation、无 pregrasp geometry 均 fail-closed。

发现 Gazebo `world` 不能直接冒充 ROS `map`。

新增转换：

```text
T_map_object
=

* inv(T_world_robot)
* T_world_object
```

Nav2 使用 map-frame object pose；Gazebo 局部物理对齐保留 raw world pose。

## 5. Phase 2.2：Agent Fetch 元任务与确定性状态机

### 动机

之前：

```text
“去拿水杯”
→ 几个 if
→ stow
→ navigate
→ pick
```

只能证明链路能跑，不能证明主脑具备可恢复、可审计、幂等的任务执行语义。

### 新增 task runtime

新增：

```text
homeagent_orchestrator/task_runtime.py
```

核心状态：

```text
STOW
  ↓ success
NAVIGATE
  ↓ success
PICK
  ↓ success
VERIFY
  ↓ postcondition
COMPLETE

failure
  ↓
RECOVERY / ABORT
```

当前恢复预算：

- Nav2 可恢复失败：最多 retry 1 次。
- Pick 可恢复失败：最多 recovery 1 次。
- Pick recovery 会重新回到 navigation，让 Context 使用最新 perception / Memory 重新计算 object pregrasp。
- Safety REJECT 直接 ABORT，不允许状态机绕过安全引擎。

### Pick 后置条件

Agent 不再只相信：

```text
SkillResult.success = true
```

Gazebo contact pick 还必须满足：

```text
contact_gated_physical_hold == true
AND
contact_required == true
```

否则视为 postcondition failure，进入 recovery 或 abort。

### DeepSeek 集成

Planner schema 新增 meta-action：

```json
{"action":"fetch","params":{"object":"cup"}}
```

DeepSeek 只负责意图层：

```text
自然语言
→ fetch(cup)
```

随后由确定性状态机拆为：

```text
stow_arm
→ navigate(object_pregrasp:cup)
→ pick(cup)
→ verify
```

每一个原子动作仍独立经过：

```text
Trusted Context
→ Safety
→ ROS2 Skill
```

DeepSeek 仍然没有权限输出 `/cmd_vel`、关节角或轨迹。

**边界：** 当前 DeepSeek API runtime 未在本阶段实测，因为 live 环境没有配置 `DEEPSEEK_API_KEY`；parser、meta-task 和 shared state machine 已由单元测试覆盖。

## 6. Phase 2.3：用户命令幂等 / 去重

### P-018 快速重复命令导致重复机械臂动作

现象：

为保证 ROS topic 送达，连续发送 3 次：

```text
机械臂检查一下
```

旧逻辑会产生 3 个独立 request，并让 MoveIt 执行 3 次。

真实语音系统、网络重试也可能出现同类问题。

### 修复

新增 `CommandDeduplicator`：

- 标准化 command 文本；
- stable command fingerprint；
- 2 秒短窗口重复命令直接 drop；
- 正在执行中的相同 fetch task 也不会重复创建。

## 7. Phase 2.4：真实 SkillResult 驱动的 Task Recovery

### V-030 状态机恢复链真实触发

真实 fetch 任务：

```text
TASK_START
→ stow success
→ navigate success
→ pick
```

第一次物理 pick 失败：

```text
GAZEBO_CONTACT_PICK_FAILED
```

Agent 没有直接结束，而是：

```text
TASK_RECOVERY
pick_recoveries=1
→ stage=navigate
→ fresh perception
→ new object_pregrasp
→ Safety
→ Nav2
```

恢复导航随后出现 `NAV2_FAILED`，状态机再次使用一次 navigation retry budget：

```text
TASK_RECOVERY
nav_retries=1
→ navigate retry
```

这证明 task progression 来自实际 ROS2 execution feedback，而不是固定 sleep / 固定脚本。

### P-019 旧 Pick 失败后仍然执行 carry 导致仿真物理发散

在上述 recovery 实验中发现：

旧 `gazebo_contact_pick_executor` 流程是：

```text
close gripper
→ 不确认是否真的抓住
→ 直接执行大幅 carry
→ 最后才检查 object 是否跟随
```

如果没有建立 grasp constraint，机械臂仍然会撞击物体/支撑台。

一次真实恢复运行中出现：

- robot / cup 坐标异常增大；
- gripper state 越过合理下限；
- Gazebo physics state 明显不可信。

结论：这是执行器闭环缺失，不能依赖“carry 完再判断”。

## 8. Phase 2.5：Grasp Proof Gate

### 修复原则

新流程：

```text
approach
→ close gripper
→ bilateral contact
→ 小幅 proof motion
→ measure object world motion
→ measure object/tool relative drift
        |
        +-- confirmed=false
        |      ↓
        |   NO CARRY
        |   open gripper
        |   return recoverable failure
        |
        +-- confirmed=true
               ↓
            full carry
               ↓
            final hold verification
```

大幅 carry 只有在 proof motion 证明杯子确实跟随 tool 后才允许执行。

### V-031 负向分支

第一版 proof motion 过小，MoveIt 判定目标已满足，`planned_points=0`。

实际：

```text
GRASP_PROBE
confirmed=False
world_motion≈0.0012m
relative_drift≈0.0000m

GRASP_ABORT
code=GAZEBO_GRASP_NOT_CONFIRMED
carry_executed=false
```

验证了 fail-safe 行为：**未确认抓取时不会执行 carry。**

### 调整

- gripper close 从 0.003m 改为合法下限 0.0m，增加双指接触稳定性；
- proof target 改为：
  ```text
  [0.20, -0.66, 1.06, -0.35]
  ```
- proof 判据：
  ```text
  cup world motion > 0.008m
  relative tool drift < 0.015m
  ```

### P-039：查明 progress checker 为何误判

新建 `scripts/nav2_telemetry.py`，用 2Hz 记录真实 ROS2 `/odom`、`/amcl_pose`、`/cmd_vel_nav`、`/cmd_vel`、`/cmd_vel_smoothed`、`/tf`；新建 `scripts/summarize_nav2_telemetry.py` 对 `Failed to make progress` 前 15 秒的平移/指令/定位误差做可复核分析。

r13 的 3 次失败窗口数据：

```text
window   odom XY displacement    mean |Nav2 linear cmd|   mean |measured odom vx|
   1         0.02499m               0.00000m/s                0.00167m/s
   2         0.02577m               0.00000m/s                0.00202m/s
   3         0.02651m               0.00000m/s                0.00196m/s
```

同一时段 Nav2 控制器要求底盘执行非零角速度（近目标原地转向/角度纠偏）；但所用 `SimpleProgressChecker` 的 `required_movement_radius=0.08m` **只以 XY 平移作为进度**，没有把正常旋转算作进度。在 15s 内平移不达 0.08m，触发错误恢复。这个判断由真实速度/里程计数据支持，不是凭猜测加大 time allowance。

已在 ROS Humble 已安装包 `/opt/ros/humble/share/nav2_controller/plugins.xml` 确认提供 `nav2_controller::PoseProgressChecker`，对应 C++ 声明可以同时检查机器人位置和航向角进展。

新 Panda 专用 Nav2 profile 正在实验：

```yaml
progress_checker:
  plugin: nav2_controller::PoseProgressChecker
  required_movement_radius: 0.08
  required_movement_angle: 0.08
  movement_time_allowance: 15.0
```

这**不禁用** progress checker，而是让原地合法角度修正也算进展。**r14 结果尚待真实验收，不得提前声称修复成功。**

### P-041：DWB 过早旋转、进度检查误判

r8 唯一一次 Failed to make progress 前 15s，独立遥测证据：

~~~text
window = 14.52 wall seconds / 14.5 sim seconds
odom XY displacement = 0.03544m
mean abs /cmd_vel_nav.linear.x = 0.00000m/s
mean abs /cmd_vel.linear.x = 0.00000m/s
mean abs /cmd_vel_nav.angular.z = 0.05263rad/s
mean abs measured odom.angular.z = 0.04997rad/s
~~~

因此机器人并非无响应，而是在仅做正负角速度微调且平移几乎为零。SimpleProgressChecker 只看 XY 位移，15s 内不到 0.08m 时误判为停滞。

检查 Panda 专用 Nav2 YAML 得到明确配置冲突：

~~~yaml
general_goal_checker:
  xy_goal_tolerance: 0.12
FollowPath:
  xy_goal_tolerance: 0.25
  trans_stopped_velocity: 0.25
  max_vel_x: 0.26
~~~

DWB 比最终 Nav2 GoalChecker 提早 13cm 进入旋转阶段，同时把几乎最大线速度当成已停止。修复为：

~~~yaml
general_goal_checker:
  xy_goal_tolerance: 0.12
FollowPath:
  xy_goal_tolerance: 0.12
  trans_stopped_velocity: 0.05
  max_vel_x: 0.26
progress_checker:
  plugin: nav2_controller::SimpleProgressChecker
  required_movement_radius: 0.08
  movement_time_allowance: 15.0
~~~

没有禁用进度 watchdog，没有放松后置条件。新增 test_panda_nav_params.py，测试 DWB 与 GoalChecker 容差一致、停止速度相对最大速度足够小、进度监测保持开启、Panda 联合碰撞半径未缩小。
