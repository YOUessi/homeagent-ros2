## 9. Phase 0.6：可信世界状态边界

识别到一个架构风险：

> 即使 LLM 不能直接控制机器人，如果允许 LLM 自己提供 `recipient_age`、`object_tags`、`forbidden_zones`，它仍然可以“伪造安全上下文”绕过规则。

因此新增 `homeagent_context`。

新链路：

```text
Agent
  ↓
ActionCandidate      ← 不可信
  ↓
Trusted Context Resolver
  ├── household memory
  └── policy
  ↓
ActionProposal       ← 带可信上下文
  ↓
Safety Engine
  ↓
Approved action
```

安全上下文只允许来自：

- Household Memory。
- 固定政策参数。
- 后续可信感知/身份系统。

LLM 返回的 context 主动丢弃。

manipulation：

```text
pick / place / handover
```

如果目标对象不存在可信 Memory：

```text
UNTRUSTED_SAFETY_CONTEXT
```

默认拒绝。

### V-007 已知对象

先向 Memory 写入已知 `cup`：

```text
pick(cup)
→ Context trusted=True
→ Safety ALLOW
→ MOCK_SKILL_COMPLETE
```

### V-008 未知对象

```text
pick(unknown_item)
→ Context trusted=False
→ Safety REJECT
→ UNTRUSTED_SAFETY_CONTEXT
```

### V-009 禁区

Policy 中：

```text
forbidden_zones = [utility_room]
```

执行：

```text
navigate(utility_room)
→ Trusted Context 注入禁区
→ Safety REJECT
→ FORBIDDEN_ZONE
```

并在观察窗口内确认没有 SkillResult。

## P-005 LLM 可以伪造安全上下文

- 状态：架构级解决。
- 风险：
  如果 LLM 输出：
  ```json
  {
    "recipient_age": 20,
    "object_tags": []
  }
  ```
  Safety Engine 无法判断这些信息是否真实。
- 根因：
  Agent proposal 与可信 world state 没有 trust boundary。
- 修复：
  新增 `homeagent_context`：
  ```text
  ActionCandidate
  → Trusted Context Resolver
  → ActionProposal
  → Safety
  ```
- 验证：
  - LLM/parser context 被丢弃。
  - unknown object -> untrusted -> reject。
  - forbidden zone 由可信策略注入。
- 结论：
  LLM 不拥有安全事实的定义权。


- 初始症状：


  3. `gh auth setup-git` 配置 HTTPS credential helper。
  4. 设置 remote：
     ```text
     origin = https://github.com/YOUessi/homeagent-ros2.git
     ```
  5. 将 Tang 本地 main 的完整历史 push 到 GitHub。
- 权限核验：
  `gh auth status` 显示 token scopes：
  ```text
  gist
  read:org
  repo
  ```
  Tang 当前可列出：
  - YOUessi 自有仓库：12 个，其中 11 public、1 private。
  - 账号当前总可访问仓库：18 个。

  ```text
  local  HEAD = 62c5fb92b4438572efb753f5326ff41d2235bc21
  remote main = 62c5fb92b4438572efb753f5326ff41d2235bc21
  ```

  local/remote SHA 完全一致。
- 结论：
  Tang -> GitHub HTTPS 认证与 push 链路已恢复，GitHub 重新成为项目代码和记录的事实源。

## 20. 本轮新增问题与修复

### P-010 Docker 内 colcon 复用了宿主 build/install 路径

- 状态：已解决。
- 症状：
  ```text
  CMakeCache.txt directory /workspace/... differs from /home/you/projects/...
  ```
- 根因：
  宿主 workspace 的 `build/`、`install/` 被 volume mount 到容器，CMake cache 记录了宿主绝对路径。
- 修复：
  Docker smoke test 使用容器独立路径：
  ```text
  /tmp/homeagent_colcon/build
  /tmp/homeagent_colcon/install
  /tmp/homeagent_colcon/log
  ```
  并通过 `--entrypoint bash` 避免 entrypoint 自动 source 宿主 install。
- 验证：
  容器内 9/9 packages build 成功。

### P-011 Docker image 缺少 C/C++ 编译器

- 状态：已解决。
- 症状：
  ```text
  No CMAKE_C_COMPILER could be found
  No CMAKE_CXX_COMPILER could be found
  ```
- 根因：
  Dockerfile 安装了运行依赖和 colcon，但没有 `build-essential`。
- 修复：
  Dockerfile 增加：
  ```text
  build-essential
  ```
- 验证：
  容器内：
  ```text
  gcc 11.4.0
  g++ 11.4.0
  ```
  9/9 ROS2 packages 成功编译。

### P-012 Gazebo server 卡在 spawn service

- 状态：已解决。
- 症状：
  robot_state_publisher 正常，但 `spawn_entity.py` 长时间等待 `/spawn_entity`，导致没有 `/odom` 和 `/scan`。
- 定位：
  world 使用：
  ```text
  model://ground_plane
  model://sun
  ```
  headless / 隔离网络环境下 Gazebo 会尝试解析外部 model database。
- 修复：
  删除外部 include，直接在 `home_room.world` 内定义 ground plane 和 directional light。
- 验证：
  HomeBot 成功 spawn，Gazebo smoke passed。

### P-013 KDL root link inertia warning

- 状态：已解决。
- 症状：
  ```text
  root link base_link has an inertia specified
  KDL does not support a root link with an inertia
  ```
- 修复：
  增加无惯量 `base_footprint` 作为根节点，通过 fixed joint 连接 `base_link`。
- 同步修改：
  - diff-drive robot base frame。
  - SLAM base frame。
  - Nav2 robot base frame。
- 验证：
  后续 Gazebo / SLAM 日志不再出现该 KDL root inertia warning。

### P-014 Nav2 launch 使用小写 false 导致 PythonExpression NameError

- 状态：已解决。
- 症状：
  ```text
  Caught exception in launch: name 'false' is not defined
  ```
- 根因：
  Nav2 Humble `bringup_launch.py` 内使用：
  ```python
  PythonExpression(['not ', slam])
  ```
  传入 `slam:=false` 后变成 Python 表达式 `not false`，而 Python 布尔量必须是 `False`。
- 修复：
  ```text
  slam: "False"
  ```
- 验证：
  Nav2 stack 成功启动，AMCL / map_server / controller / planner / bt_navigator 全部进入 active。

### P-015 Nav2 stale map→odom transform 导致“假成功”

- 状态：已解决。
- 初始症状：
  ```text
  NAV2_SUCCEEDED
  displacement_m ≈ 0.0028
  ```
  实际机器人几乎没有移动。
- Nav2 日志：
  ```text
  Transform data too old when converting from map to odom
  ```
- 根因：
  1. Nav2 stack 使用 Gazebo simulation clock，但 HomeAgent core / Nav2 skill executor 与 E2E probe 没有在该测试入口中显式启用 `use_sim_time:=true`，存在混用 wall time 与 sim time 的风险。
  2. AMCL 默认 `update_min_d=0.25`、`update_min_a=0.2`，机器人初始静止期间 `map→odom` 不会随着每个 laser scan 持续更新，进一步放大 TF stale 问题。
- 修复：
  - `homeagent_core.launch.py` 的 Nav2 demo 启动统一传入：
    ```text
    use_sim_time:=true
    ```
  - E2E probe 使用：
    ```text
    --ros-args -p use_sim_time:=true
    ```
  - AMCL：
    ```text
    update_min_a: 0.0
    update_min_d: 0.0
    ```
    使初始静止阶段也持续处理 scan 并刷新定位 TF。
- 防误判：
  `nav2_e2e_smoke.py` 继续保留双重验收：
  ```text
  NAV2_SUCCEEDED
      AND
  actual /odom displacement > 0.5 m
  ```
- 修复后验证：
  第一轮：
  ```text
  target:          living_room (0.8, 0.0)
  final_xy:        [0.6450, -0.0105]
  displacement_m: 0.6496
  NAV2_SUCCEEDED
  passed: true
  ```
  Demo 重跑：
  ```text
  final_xy:          [0.6510, -0.0082]
  displacement_m:   0.6556
  trajectory_samples: 404
  NAV2_SUCCEEDED
  DEMO PASS: True
  ```
- 结论：
  当前已经是“Nav2 action 成功 + 机器人真实移动”同时成立，P-015 关闭。
